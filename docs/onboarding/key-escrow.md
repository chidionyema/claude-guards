# Key escrow

## What this is for

Three files on this laptop cannot be regenerated by anybody. Two are age private
keys, and they are the only things that can decrypt the secret bundles the
deployed services read. The third is `estate.env`, which holds the credentials
the offsite backup uses to reach its bucket.

Until 2026-08-23 all three existed in exactly one place, on one Mac, and every
backup on the estate deliberately skipped the directory holding them. Losing the
laptop meant the bucket full of encrypted backups stayed full of encrypted
backups forever, and nothing could reach the bucket either.

Escrow puts a copy where a fire cannot reach it, without putting a readable
credential anywhere.

## How it recovers, and why it takes two accounts

The copy is split, so no single account holds anything useful:

- **Cloudflare R2** holds the encrypted blob, in the same bucket the estate
  already backs up to. On its own it is unreadable.
- **iCloud Drive** holds the one key that opens the blob, under the founder's
  Apple ID. On its own it decrypts nothing.

Recovery on a new machine is a Cloudflare sign-in and an Apple sign-in, both of
which have their own account-recovery routes that do not involve this laptop.
Those are two of the five sign-ins the rebuild already needs, so escrow adds
none.

The reason it is not simpler: the obvious answer is a passphrase, and a
passphrase has to be given to a person through some channel, which then holds a
copy of it. There is no channel here that does not keep one.

## What it costs

Nothing measurable. The blob is 10,440 bytes and is rewritten once a day, so R2
storage is a rounding error against the repository bundles already in that
bucket, and there is one PUT per day.

## What it touches

It reads three files and writes one object. It changes nothing:

    ~/.config/prospector/age-key.txt      read
    ~/.config/hermes/age-key.txt          read
    ~/.config/estate/estate.env           read
    :s3:prospector-packs/escrow/config-keys.age    written daily

Adding a fourth file is an edit to `SOURCES` in `estate/key_escrow.py`, on
purpose. A glob would quietly grow until the escrow was a copy of the home
directory, and a credential nobody reviewed would end up in a bucket.

## Where it lives

    estate/key_escrow.py          seals and verifies
    estate/recovery-key.pub       the public half, safe in git, used to encrypt
    drills/check_key_escrow.py    the weekly drill
    ai.estate.key-escrow          the launch agent, daily at 05:10

The private half is at `~/.config/estate/recovery-key.txt` and in iCloud Drive.
Neither is in git and neither ever appears in a log.

## How to turn it off

    launchctl bootout gui/501/ai.estate.key-escrow

That stops the daily reseal. The blob already in R2 stays there and stays valid,
and the drill keeps checking it, so the first thing that happens after switching
it off is that the drill goes red once a source file changes. That is intended:
a stopped escrow should be visible, not silent.

To bring it back:

    launchctl bootstrap gui/501 ~/Library/LaunchAgents/ai.estate.key-escrow.plist

## What goes wrong

**macOS blocks scheduled jobs from reading iCloud Drive.** Measured under
launchd: a scheduled job can create a file there and check that one exists, and
cannot read one or list the directory. Granting Full Disk Access would fix it and
would cost a trip through System Settings, so the design avoids needing it
instead. Nothing scheduled reads iCloud. The public key sits in git, the private
key has a second copy at `~/.config/estate/recovery-key.txt` that the drill uses,
and the iCloud copy is written once and never touched again.

The consequence is a real limit, and it is stated rather than hidden: when the
drill runs on its schedule it proves the blob opens, and it can only check that
the iCloud key is present and the right size, not that its contents are intact.
When an agent runs the same drill by hand it uses the iCloud copy directly and
proves the whole chain. The drill says which one it used, every run.

**The escrow going stale is the failure that matters**, not the escrow being
absent. An absent one is obvious. A stale one restores cleanly and opens
yesterday's ciphertext while no longer matching the keys on the laptop. The drill
compares hashes of what it restored against the live files and fails on any
difference, which is why rotating an age key turns it red until the next reseal.

**The recovery keypair is generated once and never rotated by this script.** A
new keypair orphans the blob already in the bucket. If it ever has to change, the
order is: generate, reseal, and only then remove the old key.
